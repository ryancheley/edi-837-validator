Validating a claim

  1. On the Validate page, choose an 837P (professional), 837I (institutional), or 837D (dental) file. The transaction type is detected automatically from the file.
  2. Optionally pick a plan to also check the file against that payer's companion-guide rules. Leave it on Base TR3 only to validate against the standard implementation guide alone.
  3. Select Validate. Results appear below the form, grouped by loop.

Claim files are validated in memory and are never stored — see Data & privacy. Maximum file size is 10 MB.

Reading the results

  • Each finding shows its severity (Error or Warning), a stable finding code, the message, and the segment/element it refers to.
  • Errors are spec violations that make the file invalid. Warnings are advisory — e.g. a segment the validator could not place — and do not count toward the error total.
  • The offending segment text is shown beneath each finding so you can locate it in your file without counting segments.
  • Use Download JSON or Download CSV to export the findings for sharing or triage.

Finding codes

Every finding carries a stable code whose prefix tells you the kind of problem:

PrefixMeaning
ENV.*Envelope / control-number problems (missing ISA/GS/ST/SE, count or control-number mismatch)

STRUCT.SEG.MISSINGA required segment is absent
STRUCT.LOOP.MISSINGA required loop is absent
STRUCT.UNEXPECTEDA segment that doesn't fit the spec at that position (warning)
ELEM.REQUIREDA required element or component is empty
ELEM.MINLEN / ELEM.MAXLENElement length out of range

Plans & companion guides

A plan represents a payer whose companion guide adds requirements on top of the standard TR3 rules — tightening situational elements to required, or restricting which codes are allowed.

  1. Create a plan from Plans → New plan (name and payer id).
  2. On the plan page, upload the payer's companion-guide PDF. Extraction runs in the background; the status chip updates automatically (Pending → Extracting → Needs review).
  3. If extraction fails, select Retry to run it again against the same PDF — no need to re-upload.
  4. Open the draft rule set, review and edit the rules if needed, tick Activate, and save. The rule set is only applied to validation once activated.

A plan can hold separate guides for different transaction types. When you validate a file, the plan applies the active rule set whose transaction types match the file — so an 837P upload uses the plan's 837P guide and an 837I upload its 837I guide.

History

The History page lists your past validations with their date, transaction type, plan, and error count. Open any run to see its findings again. Only the structured results are kept — never the uploaded file.

Data & privacy (PHI)

X12 837 files contain protected health information. Uploaded claim files are validated in memory and are not stored; only structured findings and metadata (filename, counts) are recorded for your history. Companion-guide PDFs are stored so they can be re-extracted. Heed any banner on the site about its compliance status before uploading real PHI.
